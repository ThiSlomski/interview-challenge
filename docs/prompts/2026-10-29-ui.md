Contrato e critérios: [UI-001](../harness/evidence/ui-plan.md).

```text

- Confira Git e o estado real antes de assumir essas condições.

Leia AGENTS.md, README.md integral, handoff e project-state. Consulte requisitos, arquitetura, SOLUTION.md, componentes, estilos e contratos das APIs conforme necessário.

Substitua a página inicial de demonstração por uma entrada útil para o desafio, com navegação clara para cadastro, login e área autenticada.

Crie uma interface coesa, responsiva e em português:

- Layout utilizável no celular e desktop.
- Labels visíveis, foco de teclado, contraste e HTML semântico.
- Estados de carregamento, vazio, sucesso e erro.
- Mensagens compreensíveis, sem mostrar códigos internos ou detalhes do servidor ao usuário.

3. Cadastro

- Trate os erros previstos pela API, incluindo conflito, limite de tentativas e indisponibilidade.

Após cadastro bem-sucedido, mostre o resumo dos dados cadastrais previsto no README, sem senha ou confirmação.
Como a API retorna somente id e cadastro não cria sessão:

- Não abra consulta pública por UUID nem enfraqueça autorização para montar o resumo.
- Não persista o resumo em localStorage/sessionStorage ou query string.
- Defina o comportamento após recarregar a página sem prometer recuperar dados que não estão disponíveis.
- Informe claramente que o usuário ainda precisa entrar para acessar a área protegida.

Clima será implementado na próxima etapa. Não mostre previsão falsa ou declare esse requisito concluído.

4. Login
- Integre POST /api/auth/login.
- Preserve a senha exatamente como digitada.
- Mostre mensagem genérica para credenciais incorretas.
- Trate carregamento, indisponibilidade e limite de tentativas.
- Deixe o navegador receber e enviar o cookie HttpOnly; não tente ler ou copiar o token.
- Após sucesso, navegue para a área protegida garantindo atualização do estado no servidor.
- Não aceite redirecionamento externo controlado por parâmetro.

5. Página protegida e consulta
- Proteja a página no servidor usando a autenticação central existente.
- Sem sessão válida, redirecione para login antes de renderizar dados protegidos.
- Falha de banco/configuração deve exibir estado seguro de indisponibilidade, sem liberar acesso nem confundir com login inválido.
- Não confie somente em useEffect, estado React ou ocultação de componentes.
- Reutilize a política de autorização e a projeção mínima; não crie uma segunda regra divergente nas páginas.
- Nunca envie hashes, material de sessão ou credenciais para componentes cliente ou payloads de renderização.
- Evite cache compartilhado de dados autenticados.

Para user, apresente seus próprios dados.
Para admin, ofereça a listagem paginada autorizada e navegação pertinente, sem expor dados a usuários comuns.
A visibilidade dos controles deve acompanhar o papel atual, mas a autorização continua obrigatória no servidor.

Não faça chamadas HTTP do servidor para si mesmo usando Host/Forwarded arbitrários. Prefira reutilizar serviços internos seguros quando necessário.

6. Logout e expiração
- Integre POST /api/auth/logout.
- Só apresente logout concluído após sucesso da revogação.
- Em falha, mostre mensagem segura e permita nova tentativa.
- Após sucesso, remova dados autenticados do estado da interface e navegue para login.
- Confira acesso por URL direta, refresh, voltar/avançar e navegação cliente após logout.
- Trate expiração durante o uso, removendo dados protegidos quando detectada.
- Não renove a sessão por navegação ou consulta.

7. Testes e inspeção
Preserve os testes existentes e acrescente cobertura significativa da interface.

Execute fluxos reais em navegador com Next e PostgreSQL descartável:
- Cadastro inválido, limites de validação, confirmação divergente e cadastro válido.
- Resumo sem senha, sem sessão automática e sem dados pessoais na URL/armazenamento.
- Login incorreto e correto.
- Página protegida por URL direta sem sessão.
- Consulta própria e listagem administrativa.
- Usuário comum impedido de obter conteúdo administrativo.
- Logout e tentativa de voltar à área protegida.
- Sessão expirada/revogada, falhas de API e limites de tentativas.
- Texto malicioso exibido como texto, sem execução de HTML/script.
- Navegação por teclado e layout em celular/desktop.

Use somente fixtures e recursos descartáveis autorizados. Não cadastre, promova ou remova usuários em imobilead para testes automatizados. Não leia dados pessoais existentes.

Pode adicionar ferramenta de teste necessária, com justificativa, versão exata e lockfile atualizado. Não afrouxe o Harness para declarar um runner sem adaptador como comprovado: registre separadamente os resultados executados.

Se navegador não estiver disponível, declare o bloqueio e diferencie testes de componentes/HTTP de teste real em navegador. Não marque E2E como aprovado sem executá-lo.

Capture telas dos estados principais com dados sintéticos para inspeção visual. Não registre cookies, senhas, URLs de conexão ou dados pessoais. Corrija problemas encontrados antes de concluir.

8. Escopo e verificação
Não implementar clima, recuperação de senha, verificação de e-mail, alteração de perfil ou novas permissões.
Preserve os contratos das APIs, migrations e grants. Qualquer ajuste necessário deve ser mínimo, justificado e receber regressão.

Execute testes pertinentes, lint, typecheck, build, audit, doctor, validate, verify --product e git diff --check. Confirme limpeza dos recursos próprios e encerramento dos processos.

9. Documentação e entrega

Sem commit, push, publicação ou acesso a bancos remotos. A integração de previsão do tempo será a próxima etapa; não a inicie neste pedido.
```

```text
Regressões:
- Resposta antiga depois de ocultar/pagehide.
- Ocultar e retornar com consulta pendente.

- Logout com consulta pendente: sucesso e falha.
- Troca de identidade.
- Timeout e recuperação.
- Histórico/cache, expiração e rebaixamento de papel.
```
