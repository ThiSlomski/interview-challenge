# PROFILE-001 — prompt autorizado

## Autorização posterior de aplicação persistente — texto integral

Autorizo aplicar no banco persistente local exclusivamente:

1. A nova migration aditiva do perfil.
2. Os novos grants necessários à edição dos campos permitidos.
3. As verificações de schema e privilégios correspondentes.

Restrições:
- Não apagar banco, schema, tabelas, usuários ou dados.
- Não executar DROP, TRUNCATE ou recriar o banco.
- Não alterar e-mail, senha, papel ou registros existentes.
- Não usar fixture descartável contra o banco persistente.
- Aplicar somente pelos comandos canônicos documentados no SOLUTION.
- Confirmar antes e depois o banco e host de destino.
- Reiniciar a aplicação após migration e grants.
- Não fazer commit ou push.

Depois, valide login com os usuários existentes e informe exatamente:
- migration aplicada;
- grants aplicados;
- schema resultante;
- privilégios resultantes;
- funcionamento do login;
- eventuais erros.

Respostas posteriores do usuário: "Posso fazer os dois logins no navegador" e,
após restart/testes, "Ambos funcionaram nos respectivos papéis". Entrada de
credenciais manual; nenhuma senha solicitada/registrada. Aplicação aprovada para
o destino local nomeado, não para outros ambientes nem para novos efeitos.
[Resultado L1](../harness/evidence/profile.md#profile-001-l1--aplicação-persistente-local-autorizada).

Ferramenta: Codex, 30/10/2026. Planejamento anterior somente leitura no chat;
este pedido altera o plano e autoriza exclusivamente a implementação do perfil.

## Pedido integral

Plano aprovado com os seguintes ajustes obrigatórios antes da implementação:

1. A exclusão administrativa será permitida somente para contas com papel `user`.
2. Contas `admin`, incluindo a conta atual, não poderão ser excluídas por esse endpoint.
3. Remova contagem do último administrador, trava consultiva global e coordenação com futuros rebaixamentos.
4. Dentro da transação, bloqueie e revalide o ator e o alvo; se o alvo for admin, recuse a operação.
5. A edição deve reutilizar as regras e limites atuais do cadastro, sem criar limites arbitrários diferentes.
6. Use `profile_version integer NOT NULL DEFAULT 1`, transportado como número.
7. Preserve o README como enunciado original; registre o estado vigente em SOLUTION, requisitos, arquitetura e evidências.
8. Divida a evolução em dois commits funcionais:
   - `feat(profile): permite editar dados do próprio cadastro`
   - `feat(admin): permite excluir usuários comuns com segurança`
9. Implemente primeiro somente a edição do perfil. Não inicie exclusão nem containerização nesta etapa.
10. Preserve todos os testes, proteções, CI e documentação existentes.
11. Não faça commit ou push.

Apresente o plano ajustado resumidamente e, em seguida, implemente apenas a edição do próprio perfil.

## Tratamento

Aceito integralmente: somente perfil implementado; segundo commit é plano, sem
exclusão iniciada. Ajustados versão integer/número e validador compartilhado;
rejeitadas propostas anteriores de limites novos, contagem/trava global para
admin e versão bigint/string. README preservado. Hipóteses/falhas/correções e
limites de aprovação na [evidência](../harness/evidence/profile.md).
